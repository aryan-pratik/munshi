# Architecture

Read `PRODUCT.md` (repo root) first. This file is *how*, not *why*. How it looks, reads and moves
is in `DESIGN.md` (repo root). AI SDK specifics are in `docs/AI_SDK_NOTES.md`; read that before
writing any AI code.

## 1. Principles

1. **Engine computes, model explains.** All numbers come from pure TypeScript in `src/engine`. The LLM narrates, drafts text, and picks between engine-generated candidates. Unit tests cover the engine; the model is never in the test path.
2. **Everything runs without a key.** Every AI surface has a **scripted** mode that streams pre-recorded responses in the *same wire format* as the live model, so the UI code path is identical. Live mode is an upgrade, not a dependency.
3. **One `World`, pure functions.** The whole business is one in-memory object (`World`). Detectors, the causal walk, the simulator, and playbooks are `(world, args) => result`. No DB, no ORM, no server state.
4. **Receipts everywhere.** Any output that makes a claim carries `evidence: RecordRef[]`. The UI renders an `EvidenceList` from refs. If you can't attach evidence, the finding doesn't ship.
5. **Static, committed seed.** `src/data/seed/world.json` is generated by a seeded script and committed. Same world every run, every machine, every demo.

Things the scaffold leaves that Phase 0 must deal with:

- **shadcn is the `base-nova` style on `@base-ui/react`**, not Radix. Popovers, menus and tooltips
  expose Base UI's attributes (`data-starting-style`, `var(--transform-origin)`), which is what

- **shadcn rewrites `src/app/globals.css` but not `layout.tsx`**, leaving
  `--font-sans: var(--font-sans)` pointing at itself. Wire the `next/font` variable for the
  family in `DESIGN.md` to `--font-sans` in `layout.tsx`.
- **`TooltipProvider` is not mounted.** Add it to the root layout.
- **`next.config.ts` ships with `cacheComponents` (and `partialPrefetching`) on.** Pages here are
  static shells with client components reading the zustand store, so this is fine; a route
  handler that reads the request body is dynamic by nature. If a build error mentions uncached
  data outside `<Suspense>`, read `node_modules/next/dist/docs` before turning the flag off.
- **`pnpm typecheck` is `next typegen && tsc --noEmit`.** A bare `tsc` fails on a fresh checkout
  because the global `LayoutProps` type only exists after Next generates `.next/types`.
- **`AGENTS.md` is generated** (Next.js agent rules pointing at `node_modules/next/dist/docs`) and
  `next dev` re-adds it if deleted. `CLAUDE.md` imports it.
- **pnpm 11 fails installs on unapproved dependency build scripts.** The script sets
  `strictDepBuilds false` for the project so that becomes a warning.
- **Peer warning:** vitest wants `@types/node` 22 or newer; the scaffold installs 20. Bump it.
- If bootstrap dies midway it leaves `package.json` behind; the script prints how to reset.

`OnsetStrip` is one metric drawn over time with the day its change began marked. `OnsetTrail`

## 4. Data flow

```
                 ┌──────────────── client ────────────────┐
  world.json ──► useWorld() ──► engine.analyze(world) + handledFindings ──► Today / Horizon / Vault
                     │                                           │
                     │ actions[]                      click "Review 7 drafts"
                     ▼                                           ▼
            applyAction(world, a)  ◄──── approve ────  ApprovalCard(drafts)
                                                                 ▲
                 ┌──────────────── server ────────────────┐      │
  POST /api/act { findingId, actions[] }                         │
        └─► replay(seed, actions) → world                        │
            └─► playbook.plan(world, finding) → steps             │
                └─► live: agent drafts messages (tools read world)│
                    scripted: engine template drafts ─────────────┘
                    (both stream data-mode first, data-plan last)
```

- **Client is the source of truth for state.** The server is stateless; every request carries the `actions[]` log and the server replays it over the committed seed. Payload stays small (actions, not the world). The store is in memory only; a hard refresh reloads the seed.
- **Today = `analyze(current world)` merged with `handledFindings(seed, actions)`.** `analyze()` returns only open findings. `handledFindings` (in `engine/index.ts`) returns `{ finding, action }[]`: for each action at index i it takes the finding with `action.findingId` from `analyze(replay(seed, actions.slice(0, i)))` (the pre-action snapshot) and uses `action.approvedAt` as the handled time. The store merges the two on every `applyAction`.
- **`/api/ask`** is the investigator agent. Tools: `getMetricSeries`, `compareWindows`, `walkCausalGraph`, `listRecords`, `getRecord`, `runSimulation`. `walkCausalGraph` returns a `Chain` whose nodes already carry their onset dates and both windows' daily series, so the client can draw the OnsetTrail straight from the tool output. The agent must cite `RecordRef`s in its final structured output. A strip with no evidence, or with no onset, is drawn labelled "unverified"; it is never hidden and never styled as fact.
- **Action names stay constant through a flow.** The playbook supplies the labels from its draft count: "Review 7 drafts" on the lead item, "Approve and send 7" in the Act sheet, "7 follow-ups sent" in the toast.
- **Scripted mode** never calls the model. `/api/ask` replays a recorded script; `/api/act` streams the engine's template drafts. The full rules (resolution table, matching, request bodies, mode signalling) are in section 5, which is the single source.

## 5. Two AI modes: contract (single source)

Both modes produce a `UIMessageStream` consumed by `useChat`, so the UI path is identical.

**Resolution** (`lib/ai/mode.ts`, server side, per request; reads `MUNSHI_AI_MODE` and whether a key or OIDC token is present):

| `MUNSHI_AI_MODE` | key or OIDC | result |
|---|---|---|
| `scripted` | any | scripted; the model is never called, even when a key exists |
| `auto` | no | scripted |
| `auto` | yes | live; if the model fails before the first streamed byte, fall back to the matching script for that request (else the plain message "I could not reach the model and have no recorded answer for this question."); the label becomes "Demo answers" |
| `live` | yes | live; failures show in the UI, no fallback |
| `live` | no | error "No AI key is configured." shown in the UI |

**Scripted matching** (`/api/ask`): by `questionId` (suggested questions send it), else fuzzy match of `text` against each script's `match` phrases; unmatched gives the polite "I only know these questions in demo mode." plus the suggestion chips. Scripted never calls the model.

**Request bodies:** `POST /api/ask { questionId?: string; text?: string; actions: Action[] }` and `POST /api/act { findingId: string; actions: Action[] }`.

**Mode signalling.** Both respond with a UI message stream whose first part is `data-mode` `{ mode: 'live' | 'scripted' }`, and whose response header `x-munshi-mode` carries the same value. The client keeps the last value and shows the "Demo answers" label when it is `scripted` (this includes a fallback to a script after a live error).

**`/api/act`.** The final part is `data-plan` `{ steps: Step[]; drafts: Draft[] }`. Scripted `/api/act` does not read `data/scripts`: it runs `playbook.plan` and streams the engine's template drafts as `data-plan`, so scripted drafts work for any finding.

**`data/scripts/*.json` exist only for `/api/ask`**: four scripts, `why-revenue-fell`, `why-complaints-up`, `which-customers-at-risk`, `what-should-i-do-today`. In live ask, the investigator's final output refers to `Chain.id` as `{ chainId, narrative, citations }`.

Scripted streams are stored as an array of UI message parts with timing hints:

```ts
// src/data/scripts/why-revenue-fell.json
{
  "id": "why-revenue-fell",
  "match": ["why did revenue fall", "revenue drop", "revenue down"],
  "parts": [
    { "type": "text", "text": "Looking at the last 14 days against the prior 14...", "delayMs": 300 },
    { "type": "tool-compareWindows", "input": {...}, "output": {...}, "delayMs": 600 },   // revenue, then revenueD2C
    { "type": "tool-walkCausalGraph", "input": { "target": "revenueD2C" }, "output": {...}, "delayMs": 1200 },
    { "type": "data-chain", "data": {
        "id": "revenueD2C:<window.to>",
        "target": "revenueD2C",
        "nodes": [   // ordered by onset: earliest cause first, the asked-about metric last
          { "metric": "adSpend", "delta": -7, "series": [/* 28 daily points */],
            "onset": "<day 77>", "onsetEvidence": [{ "source": "meta-ads", "kind": "event", "id": "evt_campaign_paused" }],
            "evidence": [...] },
          { "metric": "sessions",   "delta": -6,  "series": [...], "onset": "<day 77>", "onsetEvidence": [], "evidence": [...] },
          { "metric": "ordersD2C",  "delta": -14, "series": [...], "onset": "<day 78>", "onsetEvidence": [], "evidence": [...] },
          { "metric": "revenueD2C", "delta": -14, "series": [...], "onset": "<day 78>", "onsetEvidence": [], "evidence": [...] }
        ],
        "edges": [ { "from": "adSpend", "to": "sessions", "sign": 1, "strength": 1 }, /* ... */ ],
        "branches": [
          { "id": "landingCvr:<window.to>", "target": "landingCvr",
            "nodes": [ { "metric": "landingCvr", "delta": -28, "series": [...], "onset": "<day 79>",
                         "onsetEvidence": [{ "source": "shopify", "kind": "event", "id": "evt_theme_updated" }], "evidence": [...] } ],
            "edges": [ { "from": "landingCvr", "to": "ordersD2C", "sign": 1, "strength": 0.3 } ],   // last edge .to = rejoin node
            "branches": [] }
        ]
    } },
    { "type": "text", "text": "...but increasing ad spend isn't the best fix." }
  ]
}
```

Day placeholders are the story days in `docs/DATA-MODEL.md`; the real values are written by the recorder. The example's `delta` numbers are the verified window deltas on the seed.

**OnsetTrail groups.** The client derives the three groups from the `Chain` alone. The branch's last edge, `branch.edges[last].to`, is the **rejoin node**, a node of the primary chain. Group 1 (primary path) is the primary `nodes` before the rejoin node, in onset order. Group 2, headed "Also contributing" (drawn only when `branches` is non-empty), is the nodes of each branch, in branch order, each ordered by onset. Group 3 (shared effect) is the rejoin node and every primary node after it, the asked-about metric last. **Group order wins over onset order**: here the branch (`landingCvr`, <day 79>) is drawn above `ordersD2C` (<day 78>) even though its onset is later. For the example this gives five strips: `adSpend`, `sessions`; then `landingCvr`; then `ordersD2C`, `revenueD2C`.

Rule: **tool outputs in scripts are generated by actually running the engine on the seed**, not typed by hand (`scripts/record-scripts.ts` does this). Scripted is not fake. The exact stream-part shapes and the helper that replays them are in `docs/AI_SDK_NOTES.md`; check them against the installed SDK before relying on this example.

## 6. Key types (summary — full definitions in `src/types`)

```ts
type RecordRef = { source: SourceId; kind: RecordKind; id: string };

type Window = { from: string; to: string };            // ISO dates, inclusive

type MetricMeta = { id: MetricId; label: string; unit: 'inr'|'count'|'pct'|'days'; goodWhen: 'up'|'down' };
// METRICS in engine/metrics.ts. The UI reads label (strip name) and goodWhen (Delta colour) from it.

type Finding = {
  id: string;                    // `${detector}:${evidence[0].source}:${evidence[0].kind}:${evidence[0].id}`;
                                 // aggregate detectors (staleHighValueLeads, overdueInvoices, zombieSubscription, renewalDue) use literal `all` as the ref id; deterministic
  detector: DetectorId;
  severity: 'critical' | 'high' | 'medium' | 'info';
  group: 'needs-you' | 'worth-knowing';   // needs-you when severity is critical or high
  title: string;                 // ≤ 80 chars, plain language, contains the number
  impactINR: number;             // >= 0; rupees at stake that acting can recover or avoid (30-day run-rate unless the detector says otherwise). The Worth column, the ranking key, what the brief sums
  exposureINR?: number;          // structural exposure; shown expanded (or in Worth in ink-2 when impactINR is 0); never ranked, never summed
  confidence: number;            // 0–1, from the detector
  window: Window;
  onset: string | null;          // ISO date it began; null for forward-looking findings (then window.to is the due date)
  series: number[];              // daily points ending at window.to: 28, or more so the onset is inside. Feeds the row's OnsetStrip
  evidence: RecordRef[];
  explain: string;               // 1–2 sentences the engine can produce without an LLM
  playbooks: PlaybookId[];
};

type ChainNode = {
  metric: MetricId;
  delta: number;                 // Δ%, current 14 days vs previous 14
  series: number[];              // 28 daily points: previous 14, then current 14
  onset: string | null;          // ISO date the change began; null = none found, drawn as "timing unverified"
  onsetEvidence: RecordRef[];    // the Event the onset snapped to, if any; drawn as a flag on the axis
  evidence: RecordRef[];
};

type Chain = {
  id: string;                    // `${target}:${window.to}`; the investigator's final output { chainId, narrative, citations } refers to it
  target: MetricId; window: Window;
  nodes: ChainNode[];            // ordered by onset: earliest cause first, target last
  edges: { from: MetricId; to: MetricId; sign: 1 | -1; strength: number }[];
  branches: Chain[];             // each is a second group ("Also contributing") with its own onset; its last edge's `to` is the rejoin node on the primary chain
  narrative?: string;            // model-authored
};

// Levers are in percent points: pricePct 5 = +5%. simulator/model.ts converts once (p = pricePct / 100).
type Levers = { pricePct: number; marketingPct: number; hires: number; inventoryPct: number; followUpHours: number };
type Outcome = { revenue: number; customers: number; churnPct: number; profit: number; cashRunwayDays: number };  // the five OutcomeTable rows, per month, engine computed
type Scenario = { levers: Levers; outcome: Outcome; risk: 'low'|'medium'|'high'; riskScore: number; notes: string[] };

type Step = { id: string; label: string; kind: 'read'|'draft'|'approve'|'send'|'update'|'remind' };
type Draft = { id: string; to: RecordRef; channel: 'whatsapp'|'email'|'task'; subject?: string; body: string; refs: RecordRef[] };
type CollectionKey = keyof World;   // the World array keys
type Effect =
  | { op: 'set';    collection: CollectionKey; id: string; patch: Record<string, string|number|boolean|null> }
  | { op: 'create'; collection: CollectionKey; record: Record<string, unknown> & { id: string } };
type PurchaseOrder = { id: string; supplier: string; lines: { sku: string; qty: number }[]; createdAt: string; status: 'draft'|'sent' };  // World.purchaseOrders, starts empty

type Action = { id: string; playbook: PlaybookId; findingId: string; approvedAt: string; effects: Effect[] };
```

`Lead.thread` is `RecordRef[]` (refs to messages); there is no `MessageRef`. `Finding.series` ends at `window.to`; forward-looking findings carry the projection series and `onset: null`.

## 7. Non-goals (architecture)

- No database. If persistence is ever needed, `World` serialises to JSON; Neon via Marketplace is the obvious step.
- No auth. One tenant.
- No edge runtime, no server-held state, no websockets.
- No charting library. If a chart needs more than ~80 lines of SVG, question whether it should exist.

## 8. Product decision

The brief started from a consumer Life OS; these docs describe a chief of staff for a small
business. The Decision log in `PRODUCT.md` records that choice and what the other one would mean.
The engine shape (detectors, onsets, the walk, simulator, playbooks), this architecture,
`DESIGN.md` and the build plan carry over either way. The persona, the planted stories in
`docs/DATA-MODEL.md` and the script in `docs/DEMO.md` are what would change. The decision is
settled on the business version; the log records the alternative.
